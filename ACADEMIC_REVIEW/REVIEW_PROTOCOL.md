# მოქმედი მოცულობა და შენახვის წესი

მომხმარებლის უახლესი მითითება: თითო ციკლში დამუშავდეს მაქსიმუმ 200 უნიკალური კითხვა და შესაბამისი განმარტება. პირველი 200-ის შეფასება დასრულებულია; დაიწყე REFINEMENT_STATE.json-ის რეალური შიგთავსის წაკითხვით (ფაილის ზუსტი სახელია REFINEMENT_STATE.json).

ამ დირექტორიაში ერთად ინახება მთავარი TXT, State, Audit, Issues, Run Log, EVIDENCE_REGISTRY.json და REFINED_RECORDS.json. JSON ჩანაწერები ადამიანისთვის წასაკითხი Master-ის სტრუქტურირებული შესაბამისია; ორი დამოუკიდებელი დამტკიცებული ვერსია არ შექმნა.

REFINED_MASTER_QBANK.txt-ში შეიტანე მხოლოდ რეალურად დასრულებული ჩანაწერი. APPROVED არის ამ პროცესის სარედაქციო სტატუსი; QA არის თვითშეფასება და არ წარმოადგენს დამოუკიდებელი ადამიანური საბჭოს ან ემპირიული ფსიქომეტრიული კვლევის შედეგს.

ყოველი გაშვებისას მხოლოდ ახალი, შეცვლილი ან რეალურად გადასამუშავებელი ჩანაწერები შეარჩიე. უცვლელი APPROVED ჩანაწერის გამოტოვების წინ გადაამოწმე მისი არსებობა Master-ში და source/reviewed fingerprint-ების თანხვედრა. გადადებული დუბლიკატი უცვლელად არ დაამტკიცო. კითხვები, განმარტებები, GLOSSARY.md, AGENTS.md და AUTOMATION_CONTEXT.json მხოლოდ წასაკითხია.

კონკურენტული შენახვა: ყველა ძირითადი შედეგი ერთ commit-ში; main-ის განახლება expected_sha-ს ზუსტი შემოწმებით, force=false. უარყოფილი lease-ის შემდეგ წაიკითხე ახალი main და State, შეაჯერე შიგთავსი და მხოლოდ შემდეგ სცადე ხელახლა. ორიგინალების blob SHA-ები შეადარე უშუალოდ ახალი commit-ის მშობელთან. კომიტის დადასტურების ცალკე ჩანაწერი შეიძლება ჩაიწეროს შემდგომ პატარა commit-ში, რომელიც მიუთითებს უკვე დადასტურებულ მთავარ review commit-ზე.

ავტომატური სტრუქტურული შემოწმება: python ACADEMIC_REVIEW/validate_review.py. სკრიპტი კლინიკურ გადაკითხვას არ ანაცვლებს. მისი წარმატებული შედეგი უნდა ემთხვეოდეს State/Master/Audit/Issues-ის ფაქტობრივ რაოდენობებს.

ქვემოთ შენარჩუნებულია საწყისი სრული სამუშაო პროტოკოლი; ამ თავში მოცემული 200-კითხვის ლიმიტი და დამტკიცების მნიშვნელობის განმარტება უპირატესია.

# X. Twice-Daily Execution Safety

რადგან სამუშაო სრულდება დღეში ორჯერ, აუცილებელია ერთმანეთისგან დამოუკიდებელი გაშვებების დაცვა.

## Single-Writer Rule

ერთი და იმავე Master/State/Audit მონაცემებზე ერთდროულად არ უნდა მუშაობდეს ორი მწერალი პროცესი.

ყოველი გაშვებისას გადაამოწმე, არის თუ არა წინა ციკლი ჯერ კიდევ აქტიური.

გამოიყენე GitHub-ის მხარდაჭერილი ოპტიმისტური კონკურენტული კონტროლი ან სხვა რეალურად ხელმისაწვდომი საიმედო მექანიზმი.

მხოლოდ ფაილში ჩაწერილი დროის ნიშნული არ ჩათვალო სრულფასოვან ექსკლუზიურ საკეტად.

თუ წინა ციკლი ჯერ კიდევ აქტიურია და უსაფრთხო ექსკლუზიური მუშაობა ვერ დასტურდება:

- არ დაიწყო მეორე პარალელური რედაქტირება;
- არ გადაწერო მიმდინარე სამუშაო;
- დაასრულე ეს გაშვება სტატუსით `SKIPPED_ACTIVE_RUN`;
- დატოვე დარჩენილი კითხვები შემდეგი ციკლისთვის.

## Source Snapshot Consistency

ყოველი სამუშაო პარტია დააფუძნე კონკრეტულ `main` commit SHA-ზე.

თუ წყარო ამ პერიოდში შეიცვალა, შენახვამდე გადაამოწმე შესაბამისი კითხვების ახალი Fingerprint-ები.

არ დაამტკიცო მოძველებული ვერსია როგორც მიმდინარე.

## Safe GitHub Commit

განახორციელე მხოლოდ `ACADEMIC_REVIEW/` დირექტორიის ცვლილებები.

არ გამოიყენო force push.

თუ შესაძლებელია, Master, State და Audit ერთ ატომურ commit-ში შეინახე.

თუ გამოყენებული GitHub ინსტრუმენტები ატომურ განახლებას ვერ უზრუნველყოფს, განახლების ყოველი ეტაპის შემდეგ გადაამოწმე მონაცემთა მთლიანობა და უზრუნველყავი უსაფრთხო Recovery.

კონფლიქტის შემთხვევაში:

1. მიიღე უახლესი `main`;
2. გადაამოწმე ახალი State;
3. შეადარე უკვე დამტკიცებული ID-ები;
4. არ დაკარგო სხვა გაშვების შედეგები;
5. უსაფრთხოდ გააერთიანე ცვლილებები;
6. მხოლოდ ამის შემდეგ შეასრულე Commit.

# XI. Checkpoint and Recovery

ყოველი წარმატებით დასრულებული პარტიის შემდეგ შეინახე დადასტურებული Checkpoint.

თუ პროცესი შეწყდა:

- შემდეგ გაშვებაზე წაიკითხე ბოლო წარმატებული მდგომარეობა;
- გადაამოწმე Master/State/Audit-ის შესაბამისობა;
- აღადგინე დაუსრულებელი სამუშაო;
- თავიდან არ დაამატო უკვე დამტკიცებული ჩანაწერები;
- განაგრძე დარჩენილი კითხვებიდან.

თუ State-ში კითხვა `APPROVED` სტატუსითაა, მაგრამ Master-ში არ არსებობს, აღიქვი ეს მონაცემთა მთლიანობის შეცდომად.

თუ Master-ში ჩანაწერი არსებობს, მაგრამ State-ში არ არის, ჯერ აღადგინე შესაბამისობა.

არ გამოიყენო მხოლოდ ბოლო დამუშავებული ID როგორც მეხსიერება.

აუცილებელია თითოეული კითხვის ინდივიდუალური სტატუსისა და შიგთავსის Fingerprint-ის შენახვა.

ასევე შეინარჩუნე `review_policy_version`.

QA პოლიტიკის მომავალი ცვლილება ავტომატურად არ უნდა იწვევდეს ყველა უცვლელი კითხვის ხელახალ შემოწმებას. სრული Re-Audit შესრულდეს მხოლოდ ცალკე, მკაფიო მითითებით.
